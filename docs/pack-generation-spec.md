# 拾光拼圖圖庫生成與交付規範

版本：1.0<br>
適用：圖庫企劃、生圖、人工修圖、翻譯、Web 與 App 圖庫發布<br>
資料契約：`schemaVersion: 2`

本文件是新圖庫從企劃到發布的共同驗收標準。標示為「必須」的項目未通過即退件；標示為「建議」的項目用於維持手機拼圖的辨識度與整套品質。

## 1. 每套圖庫的交付內容

每套圖庫必須包含：

1. 一個穩定且唯一的 `packId`。
2. 原則上 10 張正式圖片；星座等具有固定集合數量的題材可例外，但須在企劃階段確認。
3. 每張圖片一個穩定且全站唯一的 `image.id`。
4. 圖庫名稱、圖庫介紹與每張圖片名稱的四語文字。
5. 每張圖片的 3:4 直式 WebP 成品。
6. 一張 240×320 的圖庫 WebP 縮圖。
7. 一份符合 v2 Schema 的 `manifest.json`。
8. 一份 `catalog-entry.json`，供總索引建置程序使用。

原始生成圖、Prompt、淘汰稿、修圖工程檔與 QA 接觸表保存在私人素材工作區，不放進公開圖庫儲存庫。

私人工作區建議固定分層：

```text
imagegen-batches/
├─ _incoming/   # 新生成、修圖與待驗收批次
├─ _accepted/   # 已接納並發布的母檔、metadata、selection 與 QA
└─ _rejected/   # 短期保留的退件候選，確認不再使用後才清理
```

已接納批次不可因 WebP 已發布就直接刪除；公開庫沒有原始 PNG 與完整 QA 工作資料。

## 2. 圖片硬性規格

| 項目 | 正式圖片 | 圖庫縮圖 |
| --- | --- | --- |
| 方向 | 直式 | 直式 |
| 比例 | 精確 3:4 | 精確 3:4 |
| 標準尺寸 | 1086×1448 px | 240×320 px |
| 格式 | WebP | WebP |
| 色彩 | RGB／sRGB | RGB／sRGB |
| 透明背景 | 不使用 | 不使用 |
| 動畫 | 不使用 | 不使用 |
| EXIF 方向 | 像素本身已轉正，不依賴 EXIF | 同左 |

### 2.1 WebP 編碼

正式圖片使用有損 WebP，現行發布工具的基準參數為：

```text
libwebp quality=82
compression_level=6
preset=picture
lossless=0
```

圖庫縮圖由正式封面產生，基準參數為：

```text
240×320 px
quality=72
method=6
```

建議正式圖片控制在 100–600 KB。若畫面品質確實需要更高容量，可超出建議值，但不得用無意義的高頻雜訊換取檔案膨脹。

### 2.2 場景文字使用原則

圖片不採「完全禁止文字」，而是只允許有敘事必要、符合現場情境且內容正確的環境文字。

可接受的文字：

- 攤位或店家的通用品項名稱，例如「鹹酥雞」「紅茶」「麵包」。
- 祭典、節慶與公共活動的通用名稱，例如「祭典」「夏祭」。
- 場所功能或方向標示，例如「入口」「出口」「車站」。
- 知名地標、古蹟或交通場景中本來就存在、且經查證正確的短標示。
- 不涉及品牌與個人的傳統書法、公共題字或文化圖樣；內容須能正確辨識，不可只是類似文字的筆畫。

環境文字必須符合以下條件：

- 內容正確、可讀且符合該地區使用的語言與年代。
- 只作為場景線索，不可比主要人物、建築、食物或物件更搶眼。
- 優先使用一至六個字的短文字；避免需要模型穩定生成整段文章。
- 生圖後須放大人工校字；任何錯字、缺筆、假字或語意不通都必須修掉或重生。

禁止的文字與識別內容：

- 註冊商標、品牌名稱、品牌 Logo、可辨識商品包裝與官方合作暗示。
- 真實人物姓名、藝名、簽名、名人肖像搭配姓名，或虛構成真實代言的內容。
- 電話、地址、電子郵件、帳號、QR Code、車牌及其他可識別個人的資訊。
- 浮水印、生成器標記、作者簽名與版權聲明。
- 無法辨識的假字、隨機字母、拼字錯誤或文字碎片。

### 2.3 其他禁止事項

- 禁止以拉伸方式把正方形或橫式圖片硬改成 3:4。
- 禁止外框、白邊、黑邊、相框或預先畫好的拼圖切割線。
- 禁止將多張獨立小圖拼貼成一張成品。
- 禁止明顯的肢體增生、融合手指、錯誤五官、斷裂建築、錯誤車輪或不合理物件結構。

## 3. 遊戲裁切與構圖安全區

遊戲不會直接把完整 3:4 母圖切片，而是先取中央 2:3 顯示區，再切成固定 2×2 四片。因此，美術驗收不能只看完整原圖。

```text
3:4 母圖（1086×1448）
┌──────────────────────────┐
│  裁掉  │ 中央 2:3 │  裁掉  │
│ 約 61px│ 顯示安全區 │約 61px │
│        ├──────┬──────┤        │
│        │ 左上 │ 右上 │        │
│        ├──────┼──────┤        │
│        │ 左下 │ 右下 │        │
│        └──────┴──────┘        │
└──────────────────────────┘
```

現行 QA 會從 1086×1448 母圖中央取約 964×1446 的 2:3 區域，左右各裁掉約 61 px，上下各裁掉約 1 px，再縮成 240×360 檢查 2×2 四片。

### 3.1 必須通過的構圖條件

- 主要人物、動物、建築或物件的辨識核心必須位於中央 2:3 安全區。
- 頭部、眼睛、主要工具、標誌性輪廓不得只存在於左右裁除區。
- 四個拼片縮小後都必須有可辨識的輪廓、材質或大色塊，不可出現兩片以上只有天空、牆面、模糊景深或純背景。
- 主體不可剛好被水平或垂直中線切斷臉部、眼睛、手掌或最重要的識別物。
- 完整圖片縮至 240×360 時，仍能在一秒內辨識主題。

### 3.2 建議的構圖方向

- 每張以一個大型主體為核心，最多一至兩個低存在感陪襯。
- 主體輪廓跨越兩個以上拼片，使組合後有明顯完成感。
- 使用大色塊、清楚明暗與有限焦點；避免滿版碎花、密集人群、過多餐盤或大量同尺寸小物。
- 同套圖庫維持一致的攝影語言、畫風、色彩邏輯與年代設定，但每張須有可區分的主色或輪廓。
- 月份、收藏品與場景系列尤其要避免「十張看起來像同一張」或縮小後只剩細碎裝飾。

## 4. 四語文字規格

語系鍵固定且順序一致：

```json
{
  "zh-TW": "繁體中文",
  "zh-CN": "简体中文",
  "en": "English",
  "ja": "日本語"
}
```

不得改用 `zh_Hant`、`cn`、`jp` 等其他代碼，也不得缺少任一語言。

### 4.1 必填文字

- 圖庫 `title`：套組名稱。
- 圖庫 `description`：整套主題、範圍與收藏感受。
- 每張圖片的 `name`：具體且可辨識的圖片名稱。

### 4.2 撰寫原則

- 四語表達同一件事，但採各語言自然語序，不做逐字硬翻。
- 繁體中文使用台灣慣用詞；簡體中文依語意轉寫，不只替換字形。
- 英文採自然標題大小寫，不堆疊形容詞或 AI 生成常見空話。
- 日文使用自然名稱與助詞，不混入英文羅馬字，專有地名例外。
- 圖片名稱須描述畫面中實際可見的主體、地點、動作或時間，不使用「圖片一」「美麗風景」「夢幻場景」等空泛名稱。
- 同一圖庫內，各語言的圖片名稱都不得重複。
- 不把 Prompt、畫風參數、攝影鏡頭或版本號寫進玩家可見文字。

建議長度：

| 欄位 | 中文 | 英文 | 日文 |
| --- | --- | --- | --- |
| 圖庫名稱 | 4–14 字 | 2–8 words | 4–18 字元 |
| 圖片名稱 | 4–18 字 | 2–10 words | 4–24 字元 |
| 圖庫介紹 | 35–90 字 | 20–55 words | 45–120 字元 |

長度為介面適配建議，不是取代語意完整性的硬性截字規則。

## 5. ID、檔名與資料夾

### 5.1 ID 規則

- `packId`：小寫英文、數字與連字號，例如 `world-night-trains`。
- `image.id`：建議格式 `<pack-id>-<兩位序號>-<主題短名>`。
- ID 一經發布即成為玩家收藏與購買紀錄的永久索引，不可因翻譯、改圖或改檔名而變動。
- 不重複使用已刪除圖片的 ID。

#### packId 建議命名方式

- 使用 2–5 個能直接描述收藏主題的英文單字，以 `kebab-case` 連接。
- 優先使用「地域／風格／對象／題材」等長期不變的語意，例如 `taiwan-night-markets`、`world-street-food`、`storybook-forest-animals`。
- 名稱須能讓開發者只看 ID 就理解內容，不依賴中文圖庫名稱才能猜測。
- 同系列可使用共同前綴，例如 `monthly-01` 至 `monthly-12`；只有確定存在固定系列順序時才使用數字。
- 發布前同時搜尋正式 catalog、既有 pack 目錄與進行中批次，確認沒有撞名或近似重複主題。
- 若撞名，加入有意義的限定詞，例如 `taiwan-street-food`，不可只加 `new`、`final`、`v2` 或隨機數字。

避免以下命名：

| 不建議 | 原因 | 建議方向 |
| --- | --- | --- |
| `pack-53` | 無法看出內容 | `world-street-food` |
| `beautiful-pictures` | 過度空泛 | `alpine-lake-villages` |
| `food-new-final` | 混入製作狀態 | `mediterranean-home-cooking` |
| `summer-2026` | 不必要綁定年份 | `summer-seaside-memories` |
| `brand-style-cats` | 可能涉及商標或仿冒 | `storybook-artisan-cats` |
| `john-doe-art` | 含人物姓名 | 以公開藝術流派或畫面題材命名 |

建立前可執行查重：

```powershell
$packId = "<pack-id>"
rg -n --fixed-strings --glob "*.json" ('"packId": "' + $packId + '"') `
  D:\PublicProjects\card-picture-packs `
  D:\GameDev2026\projects\card_picture_puzzle\imagegen-batches
```

沒有結果才代表目前未找到完全相同的 `packId`；仍須人工檢查是否已有名稱不同但題材高度重複的圖庫。

範例：

```text
packId: world-night-trains
image.id: world-night-trains-01-alpine-sleeper
file: packs/world-night-trains/v2/images/world-night-trains-01-alpine-sleeper.webp
```

### 5.2 公開交付結構

```text
packs/
└─ <pack-id>/
   └─ v<version>/
      ├─ images/
      │  ├─ <image-id>.webp
      │  └─ ...
      ├─ thumbnail.webp
      ├─ manifest.json
      └─ catalog-entry.json
```

已發布版本的 URL 與內容視為不可變。任何圖片、翻譯或 metadata 修正都必須提高 `version`，建立新的 `v<version>` 目錄，不可直接覆蓋舊檔造成 App 快取與 SHA-256 失效。

## 6. Manifest 範例

```json
{
  "schemaVersion": 2,
  "packId": "sample-pack",
  "version": 2,
  "order": 52,
  "releasedAt": "2026-08-19T00:00:00.000Z",
  "price": 50,
  "defaultLocale": "zh-TW",
  "supportedLocales": ["zh-TW", "zh-CN", "en", "ja"],
  "title": {
    "zh-TW": "範例圖庫",
    "zh-CN": "示例图库",
    "en": "Sample Collection",
    "ja": "サンプルコレクション"
  },
  "description": {
    "zh-TW": "以清楚大型主體組成、適合手機拼圖辨識的十張收藏圖。",
    "zh-CN": "由清晰大型主体组成，适合手机拼图辨识的十张收藏图。",
    "en": "Ten collectible portraits built around bold subjects that remain clear in a mobile puzzle.",
    "ja": "スマートフォンのパズルでも見分けやすい、大きな主役を描いた10枚のコレクションです。"
  },
  "artwork": {
    "orientation": "portrait",
    "aspectRatio": "3:4"
  },
  "coverImageId": "sample-pack-01-main-subject",
  "images": [
    {
      "id": "sample-pack-01-main-subject",
      "file": "packs/sample-pack/v2/images/sample-pack-01-main-subject.webp",
      "mimeType": "image/webp",
      "width": 1086,
      "height": 1448,
      "bytes": 345678,
      "sha256": "由發布工具計算的64位小寫SHA-256",
      "name": {
        "zh-TW": "晨光中的主角",
        "zh-CN": "晨光中的主角",
        "en": "The Hero in Morning Light",
        "ja": "朝日に包まれた主役"
      }
    }
  ]
}
```

`bytes`、`sha256`、`manifestBytes`、`manifestSha256` 與 `downloadBytes` 必須由發布工具依實際檔案產生，不可人工估填。

## 7. 封面與圖庫縮圖

- `coverImageId` 必須指向 manifest 內實際存在的圖片。
- 封面優先選擇縮小後仍有明確大型主體、色彩代表整套且不易與其他圖庫混淆的圖片。
- `thumbnail.webp` 固定由封面生成，不另行使用不同構圖，避免玩家進入圖庫後看到不一致的內容。
- 圖庫總覽只先載入 240×320 縮圖；玩家進入單一圖庫後才載入該包正式圖片。

## 8. 生成、修圖與 QA 流程

1. **企劃**：確認主題、張數、共同畫風、十張題材與四語暫定名稱。
2. **生圖**：以 3:4 直式構圖生成；若由舊圖延展，僅自然補足上下環境，不拉伸主體。
3. **初檢**：檢查主體數量、人物肢體、動物四肢、工具、載具、建築；若有環境文字，逐字核對內容、語言、年代與場景是否正確。
4. **中央裁切 QA**：產生中央 2:3、240×360、2×2 接觸表並逐格查看。
5. **修圖／退件**：任何一格缺乏辨識線索、主體被裁斷或出現生成瑕疵，都須修正或重生。
6. **四語定稿**：逐圖對照實際畫面命名，不依 Prompt 猜圖。
7. **發布轉檔**：由工具轉成 WebP，產生 manifest、縮圖、容量與 SHA-256。
8. **自動驗證**：執行完整 catalog 與檔案檢查。
9. **人工抽查**：在手機尺寸查看圖庫總覽、完整圖片與四個拼片。
10. **版本發布**：完成 Git 提交後再發布；不得先更新 catalog、後補圖片。

## 9. 自動驗證指令

在 `card-picture-packs` 儲存庫執行：

```powershell
npm test
npm run v2:validate
npm run build
```

只驗證尚未完成的局部圖庫時，可使用：

```powershell
npm run v2:validate:preview
```

正式驗證必須確認：

- catalog、manifest 與實際路徑一致。
- 四語欄位全部存在且非空白。
- `packId`、版本、價格、張數與封面一致。
- 所有圖片確實為有效 WebP。
- 正式圖片像素比例為精確 3:4。
- 圖庫縮圖為精確 240×320。
- manifest 與圖片的 byte 數及 SHA-256 完全一致。
- 圖片 ID 在所有圖庫中全域唯一。

## 10. 最終交付檢查表

### 美術

- [ ] 每張為 1086×1448、RGB、3:4 直式。
- [ ] 中央 2:3 與 2×2 四片均有辨識線索。
- [ ] 240×360 縮圖可快速辨識主題。
- [ ] 環境文字僅限必要且正確的通用品項、活動或公共標示。
- [ ] 無假字、錯字、商標、品牌 Logo、人物姓名、個資、浮水印與簽名。
- [ ] 無肢體、動物、建築、載具與物件結構錯誤。
- [ ] 同套風格一致，但每張輪廓或配色可區分。

### 文字與資料

- [ ] 圖庫名稱、介紹與每張圖名都有繁中、簡中、英文、日文。
- [ ] 四語語意一致且用詞自然。
- [ ] 同包圖片名稱不重複、不空泛。
- [ ] `packId` 與所有 `image.id` 唯一且不再變更。
- [ ] 封面 ID 存在於圖片清單。

### 發布

- [ ] 正式圖片與縮圖皆為 WebP。
- [ ] manifest、catalog entry、容量與 SHA-256 由工具生成。
- [ ] `npm test`、`npm run v2:validate`、`npm run build` 全數通過。
- [ ] 沒有把原始 PNG、Prompt、淘汰稿或 QA 工作檔放進公開儲存庫。
- [ ] 已發布內容若有修改，使用新版本目錄而非覆蓋舊 URL。
